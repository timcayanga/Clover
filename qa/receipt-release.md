# Live receipt check for a relevant release

Run once on each affected deployed origin with its designated fictional QA account. Use the existing large labeled receipt or an equivalent independently labeled fictional image exceeding 4.5 MB. Record the deployment ID and Git SHA from health before and after the test. For native releases, also record the installed package and backend in the release evidence and repeat on each affected platform.

Run `node qa/live-receipt.mjs <exact-live-origin> <deployed-git-sha>` for the main Split Bills API flow. It signs in to the mapped Pro account, generates a labeled large PNG, uses the app's upload client, drops the save response after commit, retries the same bytes, and checks the persisted ledger. It records proof only after the ending health check. If sign-in is blocked, retain that result and resume the release check when access changes. Use separate UI/device evidence for visible progress, item rendering and affected scoped flows.

1. Open Split Bills, pick the file, and verify the editable bill appears with the expected merchant, currency, total and lines. Record byte size, SHA-256 and time until visible.
2. In the QA browser, interrupt the first **save response after the server commits**. Record the committed bill ID in the redacted trace. Restore connectivity, retry with the exact same bytes and record the returned ID.
3. Reload the bills list and read all matching IDs. Require exactly one saved bill, the original ID, and the labeled total. For a scoped change repeat within the affected Circle, group or person and verify allocation and persistence there. Retain failed attempts. Use QA data only and leave existing bills intact.
4. Save the redacted trace to `qa/state/receipt-releases/<hostname>/<gitSha>/redacted-trace.json`. Alongside it save `result.json` with origin, gitSha, deploymentId, traceSha256, fileSha256, retryFileSha256, fileBytes, interruption ("save-response-lost"), firstBillId, retryBillId, matchingIdsAfterReload, expectedTotalMinor and actualTotalMinor. Record the trace digest after finalizing the trace. Keep screenshots and package identity with the release.
5. The daily runner checks evidence on deployed receipt-related diffs and carries missing proof forward. Unknown comparisons require verification. A native-only release must run the release check even if the backend SHA is unchanged. Reuse existing proof only for the same release, environment and scope. Daily smoke runs do not initiate uploads.

For a routine staging receipt run, use `node qa/live-receipt.mjs https://staging.clover.ph <deployed-git-sha> --smoke` with the staging test Clerk key. This allocates a fresh workspace owned by the designated staging QA user. The operator captures complete-row hashes and counts across the 21 protected tables once before both cases and compares once afterward, including after a case failure. The retained checkpoint is compared separately. A failed baseline stops uploads.

The staging coordinator holds local TCP port 55479 for the duration of the suite, including final verification. Run live receipt jobs from this coordinator. It verifies two small labeled receipts in sequence, including the exact item descriptions and amounts, currency, total, a lost save response, an identical retry and exactly one persisted bill per case. Proof is under `qa/state/receipt-smoke/staging.clover.ph/<git-sha>/<run-id>/`. A suite pass requires `passed.json`. Historical bulk runners are archived evidence. Run corpora with the disposable PostgreSQL trainer.
